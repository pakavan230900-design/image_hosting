# Сервер зображень 2.0

Веб-сервіс для завантаження та зберігання зображень. Користувач завантажує
файл — сервіс зберігає його на диску, записує метадані в PostgreSQL і повертає
пряме посилання. Завантажені зображення можна переглядати списком з пагінацією
та видаляти через веб-інтерфейс. Для бази даних передбачено резервне копіювання.

## Технології

- **Python 3.12** — бекенд на стандартній бібліотеці `http.server`
  (`ThreadingHTTPServer`), без фреймворків
- **Pillow** — перевірка, що завантажений файл справді є зображенням
- **PostgreSQL 16** — зберігання метаданих зображень
- **psycopg2** (`psycopg2-binary`) — підключення Python до PostgreSQL
- **Nginx** — роздача зображень з диска та проксування решти запитів на бекенд
- **Docker / Docker Compose** — контейнеризація всіх сервісів

## Структура проекту

```

│   └── style.css        # стилі
├── images/              # завантажені зображення (volume)
├── logs/                # app.log (volume)
```

## Вимоги до оточення

- Docker Desktop (включає Docker Compose).
- Більше нічого встановлювати не потрібно: Python, PostgreSQL, Nginx і всі
  залежності запускаються в контейнерах.

## Запуск і зупинка

Запуск з кореня проекту:

```bash
docker compose up --build
```

або у фоновому режимі:

```bash
docker compose up --build -d
```

Після запуску сервіс доступний за адресою **http://localhost:8080**.

Зупинка:

```bash
docker compose down
```

Дані при зупинці не втрачаються:

- зображення та логи лежать у папках `images/` і `logs/` на диску (bind mount);
- база даних зберігається в іменованому томі `db_data`.

Повне очищення разом з базою даних (наприклад, щоб перевірити запуск «з нуля»):

```bash
docker compose down -v
```

> Після зміни `nginx.conf` потрібно перезапустити Nginx:
> `docker compose restart nginx` — команда `up --build` перезбирає тільки бекенд.

## Архітектура

```
               :8080
Браузер ──────────────► Nginx ──┬── /images/<файл> ──► папка images/ (роздає сам)
                                │
                                └── усе інше ─────────► app (Python, :8000)
                                                          │
                                                          ├──► папка images/
                                                          ├──► logs/app.log
                                                          └──► db (PostgreSQL, :5432)
```

| Сервіс | Образ | Призначення |
|---|---|---|
| `db` | `postgres:16-alpine` | База даних. Контейнер `postgres_container`, БД `images_db`. Назовні порт не відкритий. |
| `app` | збирається з `Dockerfile` | Python-бекенд. Доступний тільки всередині мережі Docker (`expose: 8000`). |
| `nginx` | `nginx:alpine` | Єдина точка входу, порт `8080` на хост-машині. |

Бекенд стартує тільки після того, як база даних готова приймати підключення
(`healthcheck` з `pg_isready` + `depends_on: condition: service_healthy`).

## База даних

### Таблиця `images`

Створюється автоматично при старті бекенду (`CREATE TABLE IF NOT EXISTS`):

```sql
CREATE TABLE images (
    id SERIAL PRIMARY KEY,                           -- унікальний ідентифікатор
    filename TEXT NOT NULL,                          -- згенерована назва файлу (uuid)
    original_name TEXT NOT NULL,                     -- оригінальна назва від користувача
    size INTEGER NOT NULL,                           -- розмір у байтах
    upload_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP, -- час завантаження
    file_type TEXT NOT NULL                          -- формат: jpg, jpeg, png, gif
);
```

### Підключення

Параметри підключення передаються бекенду через змінні оточення
в `docker-compose.yml`:

| Змінна | Значення |
|---|---|
| `DB_HOST` | `db` |
| `DB_PORT` | `5432` |
| `DB_NAME` | `images_db` |
| `DB_USER` | `postgres` |
| `DB_PASSWORD` | `password` |

Для кожного запиту відкривається окреме з'єднання. Це безпечно для
багатопотокового сервера, де кілька запитів обробляються одночасно.

> Якщо змінити логін, пароль або назву БД у `docker-compose.yml`, потрібно
> виконати `docker compose down -v`: PostgreSQL застосовує ці налаштування
> тільки при першому створенні тому.

### Час

Контейнери працюють в UTC, тому `upload_time`, записи в `app.log` і назви
файлів резервних копій вказані в UTC.

| Маршрут | Метод | Опис |
|---|---|---|
| `/` | GET | Головна сторінка з формою завантаження |

| `/images-list` | GET | Список зображень з бази даних, по 10 на сторінці |
| `/images-list?page=N` | GET | Сторінка N списку |

## Завантаження зображень

### Обмеження

- Формати: `.jpg`, `.jpeg`, `.png`, `.gif`.
- Максимальний розмір файлу: **5 МБ**.
- Перевіряється не тільки розширення, а й реальний вміст файлу (Pillow):
  файл з підробленим розширенням буде відхилено.

### Порядок збереження

1. Файл перевіряється (розмір, розширення, вміст).
2. Генерується унікальна назва: `<uuid>.<розширення>`.
3. Метадані записуються в таблицю `images`.
4. Файл записується в папку `images/`.
5. Транзакція підтверджується (`commit`).

Якщо база даних недоступна або запис не вдався, транзакція відкочується
і **файл на диску не зберігається**. Користувач отримує повідомлення про
помилку, причина записується в `app.log`.

### Приклад через curl

```bash
curl -X POST -F "file=@photo.jpg" http://localhost:8080/upload
```

Успішна відповідь:

```json
{
  "message": "Файл успішно завантажено",
  "id": 1,
  "filename": "d55715b2bb3c480b8af53a2cdf337ca8.jpg",
  "url": "/images/d55715b2bb3c480b8af53a2cdf337ca8.jpg"
}
```

Відповідь з помилкою:

```json
{"error": "Файл перевищує максимальний розмір 5 МБ"}
```

| Ситуація | Код | Повідомлення |
|---|---|---|
| Непідтримуваний формат | 400 | `Непідтримуваний формат файлу: .txt` |
| Вміст не відповідає розширенню | 400 | `Вміст файлу не відповідає його розширенню` |
| Файл не є зображенням | 400 | `Файл не є коректним зображенням` |
| Файл більший за 5 МБ | 400 | `Файл перевищує максимальний розмір 5 МБ` |
| У запиті немає файлу | 400 | `Не вдалося знайти файл у запиті` |
| Запит не `multipart/form-data` | 400 | `Очікується Content-Type: multipart/form-data` |
| Помилка бази даних | 500 | `Помилка бази даних, файл не збережено` |

## Список зображень і пагінація

Сторінка `/images-list` показує таблицю з колонками:

| Назва файлу | Оригінальна назва | Розмір (КБ) | Дата завантаження | Тип файлу | Дія |
|---|---|---|---|---|---|
| посилання на `/images/<файл>` | назва від користувача | розмір у КБ | `YYYY-MM-DD HH:MM:SS` | `jpg` / `png` / `gif` | кнопка «Видалити» |

- Нові зображення показуються першими.
- На сторінці 10 записів. Вибірка робиться через `LIMIT` і `OFFSET`:

  ```sql
  SELECT id, filename, original_name, size, upload_time, file_type
  FROM images
  ORDER BY upload_time DESC, id DESC
  LIMIT 10 OFFSET <(сторінка - 1) * 10>;
  ```

- Під таблицею — кнопки «Попередня сторінка» / «Наступна сторінка» та
  інформація «Сторінка 2 з 3 (всього зображень: 25)».
- На першій сторінці кнопка «Попередня сторінка» неактивна, на останній —
  «Наступна сторінка».
- Некоректний номер сторінки (`0`, від'ємний, `abc`) відкриває першу
  сторінку; номер більший за кількість сторінок — останню.
- Якщо в базі немає записів, показується «Немає завантажених зображень».
- Назви файлів екрануються, тому HTML у назві файлу не виконується.

## Видалення зображень

Кожен рядок списку має кнопку **«Видалити»**. Після підтвердження браузер
надсилає запит `POST /delete/<id>`.

Що відбувається:

1. Бекенд знаходить запис з цим `id` у базі даних.
2. Видаляє запис (`DELETE FROM images WHERE id = <id>`).
3. Видаляє файл з папки `images/`.
4. Підтверджує транзакцію і перенаправляє назад на ту саму сторінку списку.

| Ситуація | Результат |
|---|---|
| Зображення видалено | перенаправлення на `/images-list`, у лог «Успіх» |
| `id` не знайдено в базі | 404 «Зображення з id=… не знайдено» |
| Файлу немає на диску | запис з БД видаляється, у лог — попередження |
| Не вдалося видалити файл | транзакція відкочується, запис залишається, 500 |
| Помилка бази даних | 500, нічого не видаляється |
| Відкриття `/delete/<id>` у браузері (GET) | 405, видалення тільки через POST |

Приклад через curl:

```bash
curl -X POST http://localhost:8080/delete/5
```

## Резервне копіювання та відновлення

Резервна копія містить базу даних `images_db` (таблицю `images` з усіма
записами). Самі файли зображень зберігаються в папці `images/` і в дамп
бази даних не входять.

### Створення резервної копії скриптом

```bash
./backup.sh
```

Перед першим запуском зробіть скрипт виконуваним:

```bash
chmod +x backup.sh
```

Скрипт:

1. Перевіряє, що контейнер `postgres_container` запущено.
2. Створює дамп через `pg_dump` у файл
   `backups/backup_YYYY-MM-DD_HHMMSS.sql`, наприклад
   `backups/backup_2026-10-11_103157.sql`.
3. Записує результат у `logs/app.log`:

   ```
   [2026-10-11 10:31:57] Дія: Успіх: резервну копію бази даних створено: backups/backup_2026-10-11_103157.sql (3237 байт).
   ```

4. При помилці (контейнер не запущено, помилка `pg_dump`, порожній дамп)
   видаляє недописаний файл, записує причину в лог і завершується з кодом 1.

Дамп створюється з параметрами `--clean --if-exists`: файл починається з
`DROP TABLE IF EXISTS`, тому відновлення працює і на порожній базі, і поверх
наявних даних (без дублювання записів).

### Створення резервної копії вручну

```bash
docker exec postgres_container pg_dump -U postgres --clean --if-exists images_db > backups/backup_$(date -u +%Y-%m-%d_%H%M%S).sql
```

Прапорець `-t` у `docker exec` тут не використовується: з ним Docker додає
символ `\r` у кінці кожного рядка, і дамп може не відновитися.

### Резервне копіювання за розкладом (необов'язково)

На macOS / Linux можна додати завдання в `cron` (`crontab -e`).
Приклад — щодня о 03:00:

```
0 3 * * * PATH=/usr/local/bin:/opt/homebrew/bin:$PATH /повний/шлях/до/image_hosting/backup.sh
```

### Відновлення з резервної копії

```bash
docker exec -i postgres_container psql -U postgres images_db < backups/backup_2026-10-11_103157.sql
```

Перевірка:

```bash
docker exec -it postgres_container psql -U postgres -d images_db -c "SELECT COUNT(*) FROM images;"
```

> Контейнер `postgres_container` має бути запущений
> (`docker compose up -d`).

## Логування

Усі дії записуються у файл `logs/app.log` у форматі:

```
[YYYY-MM-DD HH:MM:SS] Дія: <повідомлення>
```

Що логується:

| Подія | Приклад |
|---|---|
| Старт і підключення до БД | `Успіх: з'єднання з базою даних встановлено, таблиця images готова.` |
| Завантаження | `Успіх: зображення 8bc3….jpg (оригінал: photo.jpg, 645 байт, id=1) завантажено.` |
| Помилки валідації | `Помилка: непідтримуваний формат файлу (notes.txt).` |
| Перевищення розміру | `Помилка: файл перевищує ліміт розміру (6216598 байт).` |
| Помилки бази даних | `Помилка: не вдалося зберегти метадані файлу photo.jpg в базі даних, файл не збережено. Причина: …` |
| Видалення | `Успіх: зображення 8bc3….jpg (id=1) видалено.` |
| Файл відсутній при видаленні | `Попередження: файл 8bc3….jpg (id=1) відсутній на диску, видаляю лише запис з бази даних.` |
| Невідомий маршрут, файл не знайдено, доступ заборонено | `Помилка: маршрут GET /nope не знайдено.` |
| Резервне копіювання | `Успіх: резервну копію бази даних створено: …` / `Помилка: резервне копіювання не виконано. Причина: …` |

Записи з'являються також у виводі контейнера: `docker compose logs -f app`.

Запити, які Nginx обробляє сам, у `app.log` не потрапляють:

- файли більші за 50 МБ (Nginx відхиляє їх до бекенду, ліміт
  `client_max_body_size 50m`; файли від 5 до 50 МБ доходять до бекенду,
  відхиляються ним і логуються);
- запити до неіснуючих зображень за адресою `/images/<файл>`.

Їх можна переглянути в лозі Nginx: `docker compose logs nginx`.

## Безпека

- Файли перевіряються за розширенням, розміром і реальним вмістом (Pillow),
  перш ніж потрапити на диск.
- Назви файлів на сервері генеруються (`uuid`), назва від користувача
  зберігається тільки в базі даних.
- SQL-запити параметризовані (`%s`), SQL-ін'єкції неможливі.
- Захист від path traversal при роздачі файлів (`/images/`, `/static/`)
  і при видаленні.
- Назви файлів на сторінці списку екрануються (захист від XSS).
- Видалення можливе тільки методом POST з підтвердженням.
- Порт бази даних не відкритий назовні.

## Корисні команди

```bash
# стан контейнерів
docker ps

# логи бекенду в реальному часі
docker compose logs -f app

# останні записи app.log
tail -20 logs/app.log

# переглянути записи в базі даних
docker exec -it postgres_container psql -U postgres -d images_db -c "SELECT * FROM images ORDER BY id DESC LIMIT 10;"

# інтерактивна консоль PostgreSQL
docker exec -it postgres_container psql -U postgres -d images_db

# завантажити 25 тестових зображень (для перевірки пагінації)
for i in $(seq 1 25); do curl -s -F "file=@test.jpg" http://localhost:8080/upload > /dev/null; done
```
